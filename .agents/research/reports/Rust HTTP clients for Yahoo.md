# Keep ureq, fix the User-Agent, stage impersonation

The app should keep **ureq 3 as its default client**. Move from 3.5.1 to 3.5.2, keep rustls+ring as the default TLS stack, and also compile in ureq's `native-tls` (SChannel) provider so the fingerprint can be switched at runtime. The real fix is the **User-Agent**: send an honest, non-library one such as `Mozilla/5.0 (compatible; <app>/<version>)`. As of 12 November 2026, Yahoo's edge on the v8 chart endpoint rejects **known library User-Agents** (curl, python-requests, Java, Go, empty) with an instant `429 Edge: Too Many Requests`. It serves any other UA, on any TLS stack. Every standard Rust client tested got HTTP 200: ureq on rustls or SChannel, reqwest on aws-lc-rs, ring or SChannel, attohttpc and minreq. The one exception was isahc, and only because its libcurl-style default UA gave it away. Switching to reqwest buys nothing against fingerprinting. Its HTTP/2 fingerprint is as non-browser as ureq's HTTP/1.1, and it adds a tokio thread and roughly twice the binary size. Only BoringSSL-based impersonation looks like Chrome, and it is the escalation tier, not the default. It needs a tokio runtime and a CMake/NASM/libclang toolchain (wreq), or a hand-written FFI binding to the prebuilt **libcurl-impersonate** DLL. The DLL is the engine behind yfinance's proven May 2025 fix, and its blocking API matches the app's threading model. The 2025 blocks lasted days and hit OpenSSL-based clients while rustls passed, so the cheap layers (UA, runtime-switchable TLS, slow serial requests, 429-aware failover to İş Yatırım, Nasdaq, TradingView and BYOK sources) need to work before anyone writes FFI.

## Yahoo's 2026 gate is a User-Agent denylist, with TLS fingerprinting in its past

Yahoo has stacked several defences since 2023, and each wave broke a different layer. Cookie and crumb authentication arrived in mid to late 2023: yfinance 0.2.32 added "cookie & crumb to requests" in November 2023 ([yfinance releases](https://github.com/ranaroussi/yfinance/releases)). Volume-based 429s recur. In November 2024 users hit the limit after about 950 tickers, and the crumb value itself came back as the string `Edge: Too Many Requests` ([yfinance #2128](https://github.com/ranaroussi/yfinance/issues/2128)). On **18 February 2025** yfinance broke and was fixed within about an hour by replacing a hard-coded Chrome/39 UA with current browser strings ([yfinance PR #2277](https://github.com/ranaroussi/yfinance/pull/2277)). That was a pure UA block.

The **late April to May 2025** episode is the one that matters for TLS choice. A yfinance user found the endpoint worked in a browser and with curl but "consistently" returned 429 from Python `requests` "with identical headers in all tests", and suspected TLS fingerprinting ([yfinance #2422 comment](https://github.com/ranaroussi/yfinance/issues/2422#issuecomment-2840759533)). The Rust evidence is cleaner still. In the `yahoo_finance_api` crate, enabling reqwest's `native-tls` or `native-tls-alpn` produced 429s, and forcing `.use_rustls_tls()` fixed them "regardless of additional reqwest features" ([yahoo_finance_api #76](https://github.com/xemwebe/yahoo_finance_api/issues/76)). Changing the UA alone had not helped ([#74](https://github.com/xemwebe/yahoo_finance_api/issues/74)). Same crate, same headers, different ClientHello, different outcome: Yahoo was evaluating TLS then. Something else happened in the same weeks. Portfolio Performance's long-standing Safari 17.3.1 UA got 429 even from curl, while old Chrome/32 and Firefox/25 strings got 200 "on different systems and country IPs". So heavily used UA strings were being denylisted independent of TLS ([PP forum 32845](https://forum.portfolio-performance.info/t/downloadfehler-bei-versuch-1-yahoo-finance/32845)). The next break, **31 December 2025**, was UA-based again. yahoo-finance2's own library UA got 429 on getcrumb, and version 3.11.1 fixed it with an "honest working user-agent" ([yahoo-finance2 #977](https://github.com/gadicc/yahoo-finance2/issues/977)). Per-IP blocks appeared in January and February 2026: one Singapore server stayed blocked while other IPs worked ([yahoo-finance2 #982](https://github.com/gadicc/yahoo-finance2/issues/982)).

The 12 November 2026 live probes show where the rule stands now. Against `query1.finance.yahoo.com/v8/finance/chart/AAPL` with no cookie or crumb, curl/Schannel over HTTP/1.1 returned **429 `Edge: Too Many Requests` (23 bytes)** for `curl/8.21.0`, `python-requests/2.32.3`, `python-httpx/0.27.0`, `Java/17.0.2`, `Go-http-client/1.1` and `Python-urllib/3.12`, and plain 429 for an empty UA. The same stack got **200** for a Chrome UA, bare `Mozilla/5.0`, `reqwest/0.12` and `okhttp/4.12.0` ([endpoint](https://query1.finance.yahoo.com/v8/finance/chart/AAPL?range=5d&interval=1d)). Python urllib on OpenSSL 3.5.7 got 200 with a Chrome UA and 429 with its default UA. The rejects were instant and came within seconds of 200s from the same IP, so this is an edge rule keyed on the UA string, not a volume limit. The response headers show `server: ATS` behind Envoy, Yahoo's own Apache Traffic Server rather than Cloudflare or Akamai ([query2 endpoint](https://query2.finance.yahoo.com/v8/finance/chart/AAPL?range=5d&interval=1d)). ATS ships JA3, JA4 and JA4H fingerprint plugins, so Yahoo can switch TLS fingerprinting back on at any time ([ATS JA4 plugin](https://docs.trafficserver.apache.org/en/latest/admin-guide/plugins/ja4_fingerprint.en.html), [ATS JAx plugin](https://docs.trafficserver.apache.org/en/latest/admin-guide/plugins/jax_fingerprint.en.html)). No official Yahoo statement on any of this exists. Everything above is reverse-engineered from client behaviour, and the evidence comes from one residential IP on one day.

The v8 chart endpoint needs **no cookie and no crumb**. v7 quote returns 401 "User is unable to access this feature" and v10 quoteSummary returns 401 "Invalid Crumb" ([v7 quote](https://query1.finance.yahoo.com/v7/finance/quote?symbols=AAPL)). yfinance's own code notes that "chart API works without its cookie" ([yfinance data.py](https://raw.githubusercontent.com/ranaroussi/yfinance/main/yfinance/data.py)). yahoo-finance2 marks only `options`, `quote`, `quoteSummary` and `screener` as `needsCrumb` ([yahoo-finance2 on npm](https://www.npmjs.com/package/yahoo-finance2)). Since getcrumb has been the most frequent 429 trigger across all these projects, a chart-only client avoids most of the historical failure surface.

## Every standard Rust client passes today, and ureq 3 is the cheapest fit

All the mainstream crates are maintained except surf, which last released in November 2021 and last pushed in 2023 ([crates.io surf](https://crates.io/api/v1/crates/surf)). The decision comes down to threading model, cookie support and cost. In a single-shot test on 12 November 2026 with `User-Agent: x`, every client that set its own UA fetched the ~35.7 KB AAPL chart body. Sizes and clean-build times below come from the research machine: Windows 11, rustc 1.98.1, x86_64-pc-windows-msvc, release profile `opt-level="s"`, LTO, one codegen unit, stripped, with a fresh target directory for each configuration. A second run without LTO produced the same ranking: ureq+SChannel 0.96 MiB in 6 s, ureq+ring 2.20 MiB in 12 s, reqwest+SChannel 2.71 MiB in 16 s, reqwest default 4.98 MiB in 30 s.

Three conclusions follow from the table. First, **ureq 3 already covers everything this app needs**. It has pooled HTTP/1.1, a per-agent cookie jar, gzip and brotli, env and Windows-registry proxies, and phase-budgeted timeouts (`timeout_global`, `timeout_connect` covering DNS and TLS handshake, `timeout_per_read`). It is a fraction of reqwest's size and build time ([ureq README](https://github.com/algesten/ureq/blob/main/README.md)). Version 3.5.0 added `Agent::shutdown()` to interrupt in-flight requests, which is useful when a gpui window closes. 3.5.1 fixed the Cookie header to send only names and values, and 3.5.2 applies body limits after decoding ([ureq CHANGELOG](https://github.com/algesten/ureq/blob/main/CHANGELOG.md)). Second, **reqwest is not a fingerprint upgrade**. It works from gpui background tasks via `reqwest::blocking`, because gpui's executor is not tokio. But it brings tokio as a hard dependency plus one internal OS thread per blocking client ([reqwest blocking/client.rs](https://github.com/seanmonstar/reqwest/blob/master/src/blocking/client.rs)), and as shown below its HTTP/2 fingerprint is no more browser-like. Third, the **libcurl-based crates carry a UA trap**. isahc's default UA got the same 23-byte edge reject as `curl/8.21.0`, so any libcurl client must set its own UA for Yahoo.

attohttpc and minreq are smaller, but neither has a cookie jar, which closes the crumb door if the app ever needs v7 or v10. attohttpc's MPL-2.0 is also an outlier among MIT/Apache crates. nyquest is the interesting dark horse: it delegates to WinHTTP and so inherits the user's system proxy settings. But it has about 2.7K downloads in 90 days, and on Windows it presumably presents an SChannel fingerprint (inferred, not measured). One gap remains open: nobody checked whether gpui-kit 0.9.1 already pulls tokio or reqwest transitively. If it does, reqwest's marginal cost drops, though its fingerprint argument does not change.

## No cheap TLS backend makes a Rust client look like a browser

The fingerprint measurements, taken on 12 November 2026 against tls.peet.ws and browserleaks with a Chrome/142 UA on every probe, show that the stack choice decides **which non-browser you resemble**, not whether you resemble Chrome.

Sources: measured via [tls.peet.ws](https://tls.peet.ws/api/all) and [browserleaks](https://tls.browserleaks.com/json); Yahoo via [query2 v8 chart](https://query2.finance.yahoo.com/v8/finance/chart/AAPL?range=5d&interval=1d); JA4 field rules from the [FoxIO JA4 spec](https://github.com/FoxIO-LLC/ja4/blob/main/technical_details/JA4.md).

**rustls** shares no part of its JA4 with Chrome. It offers ten ciphers including the `0x00ff` SCSV, no GREASE, no ALPS, ECH, compress_certificate or SCT, and no ALPN at all in ureq. Its JA3 changes on every connection because rustls 0.23 randomises extension order, so only JA3N, JA4 and peetprint can pin it. The crypto provider changes only the last hash segment. aws-lc-rs advertises X25519MLKEM768, but last and without a key share, so neither provider looks more like a browser. Stock rustls cannot impersonate at all: the ClientHello-customisation request is still an open upstream thread ([rustls #1932](https://www.github.com/rustls/rustls/issues/1932)), and the craftls fork last released in January 2024 ([craftls](https://github.com/3andne/craftls)). The public JA4 database now returns 403 without an account, so no one could check whether `61a7ad8aa9b6` is labelled anywhere ([ja4db.foxio.io](https://ja4db.foxio.io/)).

**SChannel is not a shortcut to looking like Edge.** Chromium Edge does its own TLS through BoringSSL and "no longer uses Windows' SChannel (except for IEMode tabs)" ([textslashplain](https://textslashplain.com/2020/02/26/can-i-in-the-new-edge/)). SChannel sends 20 ciphers including legacy CBC and RSA key-exchange suites, key-shares all three curves, and includes SHA-1 signature algorithms. Its JA4 prefix `t13d201100_2b729b4bf6f3` is **exactly the a+b segment FoxIO publishes as its IcedID malware example** ([FoxIO JA4 README](https://raw.githubusercontent.com/FoxIO-LLC/ja4/main/README.md)). That is less damning than it sounds. The prefix belongs to every program riding the OS stack, including curl.exe, PowerShell and WinHTTP clients, so it is common rather than rare. But the c-hash depends on the Windows build, so different users' machines will send different fingerprints that the developer cannot test (inferred from FoxIO's note that "Windows functions will be unique", [APNIC blog](https://blog.apnic.net/2023/11/22/ja4-network-fingerprinting/)).

**HTTP/2 does not help either.** reqwest's hyper/h2 SETTINGS frame and pseudo-header order (`m,s,a,p`) differ from Chrome's (`m,a,s,p`) whichever TLS backend sits underneath. reqwest also sends just two headers where Edge sends thirteen. Detection vendors check exactly this kind of cross-layer consistency ([Scrapfly HTTP/2 guide](https://scrapfly.io/blog/posts/http2-http3-fingerprinting-guide), a vendor source). Every successful Yahoo probe in November 2026 ran over HTTP/1.1, so h2 is not required.

The TLS recommendation therefore rests on track record and controllability, not mimicry. **Default to rustls+ring.** It is the stack that fixed the May 2025 Rust block, and Wealthfolio, yahoo_finance_api and yfinance-rs all run it in production. Every user sends the same fingerprint, so what the developer tests is what users send. That uniformity cuts both ways (an inference): if Yahoo blocks that hash, every install fails at once. That is why the second stack is worth carrying. ureq lets an agent pick `TlsProvider::NativeTls` at runtime ([ureq README](https://github.com/algesten/ureq/blob/main/README.md)), so compiling both features gives a one-line switch to a completely different, very common Windows fingerprint. It costs about 1 MB, needs no new code paths, and needs no toolchain. ring builds with only the VS Build Tools ([ring BUILDING.md](https://github.com/briansmith/ring/blob/main/BUILDING.md)). aws-lc-rs also built on the research machine without NASM, but its docs list NASM for x86_64 MSVC ([aws-lc-rs Windows requirements](https://github.com/aws/aws-lc-rs/blob/main/book/src/requirements/windows.md)), and it costs more size and build time for no fingerprint benefit.

## Browser impersonation costs a toolchain and a runtime, so hold it in reserve

If Yahoo re-enables fingerprint rules that reject both rustls and SChannel, the only remedy is a client whose ClientHello and HTTP/2 frames match a real browser. As of November 2026 the Rust options split into one mature crate family, one prebuilt C library and several traps.

The two serious candidates trade off differently. **wreq** is a hard fork of reqwest with the widest profile catalogue and frequent releases. It would need a dedicated background thread running a tokio current-thread runtime that `block_on`s each request. It would also need NASM and LLVM installed on every build machine, and the rolling MSRV keeps the compiler pinned to the latest stable ([wreq README](https://raw.githubusercontent.com/0x676e67/wreq/main/README.md)). The bus factor is one person (0x676e67 maintains wreq, wreq-util and btls), and the sponsor list is antibot-bypass vendors. The license history is a hidden risk: a lockfile resolving to wreq-util 0.1.0 pulls GPL-3.0 code, so pin **≥0.2.0** ([wreq-util versions](https://crates.io/api/v1/crates/wreq-util/versions?per_page=100)). BoringSSL exports OpenSSL-named symbols, and wreq's `prefix-symbols` fix is documented only for Linux and Android, so openssl-sys must stay out of the tree.

**libcurl-impersonate** is the same engine curl_cffi wraps, and curl_cffi is the only impersonation stack with real Yahoo production history. Its `curl_easy_perform` is synchronous, so it drops into gpui background tasks exactly where ureq calls sit today. The DLL keeps its BoringSSL symbols behind a module boundary. It also brings cookies, proxies, timeouts and HTTP/2 along. The costs are real. No maintained Rust binding exists: no `curl-impersonate-sys` exists, the wrapper crates have under 2K downloads ([crates.io search](https://crates.io/api/v1/crates?q=curl-impersonate&per_page=10)), and curl-sys cannot simply be pointed at the impersonate library ([curl-sys build.rs](https://raw.githubusercontent.com/sagebind/curl-rust/main/curl-sys/build.rs)). So the app would carry a small unsafe FFI layer, ship a DLL, and track security releases such as v2.3.1's brotli fix. yfinance's own experience is a warning: curl_cffi brought new failure modes, including Windows certificate-location errors ([yfinance #2450](https://github.com/ranaroussi/yfinance/issues/2450)), forced version bumps over a CVE, and profile names drifting out of sync ([yfinance CHANGELOG](https://raw.githubusercontent.com/ranaroussi/yfinance/main/CHANGELOG.rst)).

The recommendation is to **build the seam now and the impersonation tier only when needed**. Put one `fetch(request) -> response` trait in front of ureq. If Yahoo starts rejecting both default stacks, implement it with libcurl-impersonate. Loading the DLL at runtime (for example via `libloading`) would keep it out of the default build and let it ship only when needed; this is a design inference, not something any project here has tried. Choose wreq instead if staying in safe Rust matters more than toolchain and runtime cost. Two rules apply to either. Send the **browser UA that matches the impersonated profile**: yfinance 0.2.59 found that overriding curl_cffi's UA hurt ([yfinance releases](https://github.com/ranaroussi/yfinance/releases)). And impersonation does nothing for per-IP limits, which the January 2026 Singapore case shows are real.

## Fallback sources need timeouts and honest headers more than fingerprints

None of the fallback sources showed TLS-level gating in the November 2026 probes. Their failure modes are slowness, hangs and in-band errors, which ureq's timeout budgets handle directly. **İş Yatırım's** `HisseTekil` and `OneEndeks` endpoints are intermittently slow, and borsa-mcp raised its timeout to 15 s after 5 s probes timed out ([borsa-mcp PR #3](https://github.com/biNom-Highend-Engineering/borsa-mcp/pull/3)). They also report errors as HTTP 200 with `"ok":false`. Give that host a 15 s global budget and validate the body, not just the status. The **Nasdaq.com API** hung until a 20 s timeout on curl's default UA, but answered both an empty UA and `ureq/2.10.0` ([live call](https://api.nasdaq.com/api/quote/AAPL/info?assetclass=stocks)). It is the one fallback that behaves like a bot filter. That makes the honest-UA choice doubly right. If the front end is Akamai, which is unverified, a Chrome UA on a rustls ClientHello is exactly the cross-layer mismatch such vendors score. A short `timeout_connect` plus `timeout_global` keeps a hang from stalling a refresh. The **TradingView scanner** (`POST scanner.tradingview.com/turkey/scan`) returned 200 to a `Rust-reqwest/0.12` UA ([borsapy README](https://github.com/saidsurucu/borsapy)), and ureq's `json` feature covers the POST body. **EODHD and Tiingo** are official keyed APIs where the client library is irrelevant. The only client-side rules are HTTPS and keeping the user's key out of logs and error strings. Tiingo requires per-user tokens and attribution ([Tiingo developer appendix](https://www.tiingo.com/documentation/appendix/developers)). Per-client fingerprint behaviour on these hosts was not measured beyond the UA probes, so the same single ureq agent with per-host timeouts is a reasonable default, not a proven one.

## The rules: one UA policy, two TLS stacks, no crumb, slow 429s

The escalation ladder below orders remedies by cost. Each step is triggered by a specific symptom, so the app does not jump to FFI on an ordinary rate limit.

| Tier | Client | Trigger to move up | Cost |
|---|---|---|---|
| 0 | ureq 3.5.2, rustls+ring, honest UA, v8 chart, serial requests | 429 on the **first** request of a session, persistently, on both query1 and query2 | None (current stack) |
| 1 | Same agent rebuilt with `TlsProvider::NativeTls` (SChannel), selectable at runtime or by remote flag | Tier 0 rejected while Tier 1 succeeds → stay; both rejected → Tier 2 | ~1 MB, no new code paths |
| 2 | Browser impersonation behind the fetch trait: libcurl-impersonate DLL (blocking) or wreq + wreq-util on a private tokio thread | Both stacks rejected while a browser on the same IP works | FFI layer or tokio + BoringSSL toolchain; 4+ MB |
| 3 | Market fallbacks: İş Yatırım / TradingView (BIST), Nasdaq (US), EODHD / Tiingo BYOK (all), manual entry | Any tier exhausted, or a per-IP block that no client can fix | Already in the feed design |

| Area | Do | Don't |
|---|---|---|
| **User-Agent** | Send a stable, honest string such as `Mozilla/5.0 (compatible; <app>/<version>)`, the pattern yahoo-finance2 has used in production since January 2026 ([#977](https://github.com/gadicc/yahoo-finance2/issues/977)). Keep PP's random `Mozilla/5.0 (NNNNNN)` as a fallback UA ([OnlineHelper.java](https://github.com/portfolio-performance/portfolio/blob/master/name.abuchen.portfolio/src/name/abuchen/portfolio/util/OnlineHelper.java)). Set it explicitly on every request or agent | Rely on any library default (isahc's got 429). Send empty, `curl/*`, `python-requests/*`, `Java/*` or `Go-http-client/*`. Copy one popular fixed browser UA (PP's Safari 17.3.1 was denylisted). Claim Chrome on a rustls or SChannel stack; that mismatch is untested as a risk with Yahoo but is exactly what detectors look for |
| **TLS backend** | Default to rustls+ring. Compile ureq's `native-tls` as a runtime-selectable second fingerprint. Under impersonation, pair the TLS profile with its own browser UA | Treat SChannel as "looks like Edge" (it does not). Pick aws-lc-rs for fingerprint reasons (it only changes the c-hash). Bring in openssl-sys alongside any BoringSSL client |
| **Feature unification** | Run `cargo tree -e features -i native-tls`, `-i aws-lc-rs` and `-i rustls` after every dependency change, gpui-kit included. With reqwest, force the backend in code, as yahoo_finance_api did in "Always use rustls TLS backend" ([PR #78](https://github.com/xemwebe/yahoo_finance_api/pull/78)) | Assume your own `default-features = false` protects you. In June 2025 an unrelated crate (ollama-rs) re-enabled reqwest's native-tls and brought the Yahoo 429 back ([#79](https://github.com/xemwebe/yahoo_finance_api/issues/79)). ureq never auto-selects native-tls from features alone, but it does adopt any rustls process-default provider, and rustls's `prefer-post-quantum` default feature reorders key groups if another crate enables it. Both change the fingerprint silently |
| **Crumb** | Skip it: v8 chart needs none. If v7 or v10 is ever added, use `fc.yahoo.com` for the A3 cookie, then `getcrumb`. Cache the crumb, refresh only on 401/403/"Invalid Crumb", and treat a crumb body of `Too Many Requests` as a 429 ([yfinance PR #2491](https://github.com/ranaroussi/yfinance/pull/2491)). Space the cookie, crumb and data calls apart | Fetch a crumb per request, or chain cookie, crumb and data in rapid succession. Bootstrap from finance.yahoo.com HTML, which hits EU consent redirects ([yfinance data.py](https://raw.githubusercontent.com/ranaroussi/yfinance/main/yfinance/data.py)). Hard-fail when ad-blockers DNS-block `fc.yahoo.com` ([PR #2483](https://github.com/ranaroussi/yfinance/pull/2483)) |
| **429 handling** | Check content type and JSON shape before parsing; a 429 body surfaced as `DeserializeFailed` in yahoo_finance_api ([#76](https://github.com/xemwebe/yahoo_finance_api/issues/76)). Treat an instant 429 on a session's first call as **classification** (escalate a tier) and a 429 after many calls as **rate limiting** (back off). Use a circuit breaker per source: open after 5 failures, retry after 60 s, close after 2 successes, the Wealthfolio template ([circuit_breaker.rs](https://github.com/wealthfolio/wealthfolio/blob/main/crates/market-data/src/registry/circuit_breaker.rs)). Then fail over to the next source | Retry 429s in a tight loop. Assume a 429 means volume; Yahoo uses the same `Edge: Too Many Requests` body for both ([yfinance #2128](https://github.com/ranaroussi/yfinance/issues/2128)). Fan out in parallel. PP runs one request at a time, yahoo-finance2 runs four concurrently ([npm](https://www.npmjs.com/package/yahoo-finance2)), and yahoo_finance_api's optional governor defaults to 10 req/s ([Cargo.toml](https://docs.rs/crate/yahoo_finance_api/5.0.0/source/Cargo.toml)) |
| **Timeouts and lifecycle** | Set `timeout_connect` and `timeout_global` on every agent, with 15 s for İş Yatırım. Call `Agent::shutdown()` when the window closes | Leave Nasdaq-style hangs unbounded, or let background tasks outlive the UI |

## Conclusion

The 2025 crisis made TLS look like the decisive variable, and for a few weeks it was. But the durable fixes across five ecosystems were cheaper: a non-denylisted User-Agent, a TLS stack that differs from the one being punished, and fewer crumb calls. By November 2026 Yahoo's own edge serves rustls, SChannel and OpenSSL alike and filters on the UA string. The useful framing for a desktop app is therefore **diversity of cheap fingerprints, not fidelity to a browser**. Two stacks selectable at runtime, an honest UA, and a source chain that degrades to İş Yatırım, Nasdaq or a user's own key cover every documented failure mode except a full return to browser-only TLS. That scenario has not occurred for rustls clients in any reported case. Impersonation remains a real option, but it is a maintenance commitment (profile drift, DLL security updates, a single upstream maintainer), and one to take on only when Yahoo forces it.

Two things remain unknown and should be watched rather than guessed. First, whether Yahoo's ATS fingerprint plugins weigh JA4 against the UA, which would make an honest UA on rustls safer than a Chrome UA on rustls. That is likely but unproven. Second, how the app behaves under sustained polling from many installs. Every measurement here was a handful of requests from one residential IP. The cheapest insurance is telemetry the app already controls: log which tier and source served each price, and how each 429 was classified, so the next Yahoo policy change shows up as data rather than as user bug reports.
